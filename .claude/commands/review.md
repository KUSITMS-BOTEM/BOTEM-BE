# Backend PR Review Guide

## 사용법

```text
/review <비교 기준 브랜치>
```

비교 기준을 생략하면 현재 브랜치 유형에 따라 `develop` 또는 `main`을 사용한다.

## 목적

Kotlin + Spring Boot 백엔드 코드를 PR 생성 전에 검토한다. 단순한 스타일보다 설계, 안정성, 성능, 보안, 데이터 정합성과 유지보수성을 우선한다.

## 리뷰 기본 원칙

- 문제의 이유와 구체적인 개선 방향을 함께 제시한다.
- 불필요한 nitpick을 지양한다.
- 실제 확인된 문제와 잠재적인 위험을 구분한다.
- 변경된 코드와 직접 관련된 문제를 우선한다.
- 충분한 근거가 없는 문제를 단정하지 않는다.
- 리뷰 과정에서 코드를 직접 수정하지 않는다.

## 1. 아키텍처와 설계

- Controller, Service, Repository의 책임이 명확한가?
- 비즈니스 로직이 적절한 계층 또는 도메인 객체에 위치하는가?
- Service가 지나치게 비대하지 않은가?
- 계층 간 의존성 방향이 적절한가?
- 펀딩 개설, 메시지 작성, 참여 로직의 책임이 명확하게 나뉘는가?

## 2. 도메인 모델

- Entity가 비즈니스 규칙을 표현하는가?
- public setter 대신 의미가 명확한 상태 변경 메서드를 사용하는가?
- 펀딩 상태와 참여 가능 조건의 불변식이 유지되는가?
- 모집 종료, 목표 금액, 참여 금액과 같은 규칙이 도메인에 일관되게 적용되는가?

## 3. 인증과 보안

- 로그인 사용자 확인과 인가 검증이 누락되지 않았는가?
- 펀딩 개설자와 참여자의 권한이 올바르게 구분되는가?
- JWT의 서명, 만료 시간과 발급 주체를 검증하는가?
- 토큰, 개인정보와 결제 관련 정보를 로그에 출력하지 않는가?
- 외부 API 응답을 검증 없이 신뢰하지 않는가?

## 4. 예외 처리

- 비즈니스 예외와 시스템 예외가 구분되는가?
- 프로젝트의 `ErrorCode`, `BusinessException`, `ApiResponse` 형식을 사용하는가?
- 적절한 HTTP Status를 반환하는가?
- 내부 예외 메시지나 민감 정보가 응답에 노출되지 않는가?
- 의미 없는 `RuntimeException`이나 과도한 `try-catch`를 사용하지 않는가?

## 5. 트랜잭션

- 쓰기 작업에 `@Transactional`이 적용되는가?
- 조회 작업의 `readOnly` 설정이 적절한가?
- 외부 API 호출이 불필요하게 트랜잭션 안에 포함되지 않는가?
- self-invocation으로 트랜잭션이 적용되지 않는 경우가 없는가?
- 참여 처리 실패 시 금액과 참여 상태가 함께 롤백되는가?

## 6. 성능과 쿼리

- N+1 쿼리가 발생할 가능성이 있는가?
- 반복문 안에서 DB를 조회하거나 저장하지 않는가?
- 홈, 위시리스트, 펀딩 목록 조회에 페이징을 적용하는가?
- 필요한 컬럼과 연관관계만 조회하는가?
- Fetch Join과 페이징을 안전하게 함께 사용하는가?

## 7. 동시성과 데이터 정합성

- 동시에 펀딩에 참여할 때 금액이나 참여 인원이 유실되지 않는가?
- 중복 참여와 중복 위시리스트 등록을 방지하는가?
- 조회 후 검증만으로 중복이나 한도 초과를 막고 있지 않은가?
- DB Unique Constraint가 필요한 데이터에 적용되는가?
- 필요한 경우 낙관적 락 또는 비관적 락을 검토했는가?

## 8. 테스트 가능성

- 주요 비즈니스 로직을 독립적으로 테스트할 수 있는가?
- 펀딩 개설, 메시지 작성, 참여 성공 및 실패 케이스를 검증하는가?
- 목표 금액, 마감 시각, 최소·최대 참여 금액의 경계값을 검증하는가?
- 외부 API 의존성을 대체할 수 있는가?
- 동시 참여에 대한 테스트가 필요한가?

## 9. 코드 가독성과 유지보수성

- 이름만으로 역할과 의도가 드러나는가?
- 불필요한 추상화나 중복 코드가 없는가?
- 지나치게 복잡한 조건문이 없는가?
- 과도한 메서드 분리나 Scope Function 중첩이 없는가?
- 프로젝트의 공백 4칸 들여쓰기와 파일 구조를 따르는가?

## 10. API 설계

- HTTP Method와 Status Code가 적절한가?
- Request와 Response DTO가 명확하게 구분되는가?
- Entity를 API 응답으로 직접 반환하지 않는가?
- 요청 데이터에 필요한 Validation이 있는가?
- `ApiResponse` 형식이 일관되게 적용되는가?
- 인증 및 인가 처리가 누락되지 않았는가?

## 11. 데이터베이스

- Entity 매핑과 실제 스키마가 일치하는가?
- Nullable, Unique, Foreign Key 정책이 비즈니스 규칙과 맞는가?
- 조회 조건에 필요한 인덱스가 있는가?
- Enum 저장 방식이 안전한가?
- 금액 데이터에 적절한 타입과 정밀도를 사용하는가?

## 12. Kotlin 코드 품질

- Null Safety를 적절하게 활용하는가?
- 불필요한 `!!` 연산자를 사용하지 않는가?
- 변경되지 않는 변수에 `val`을 사용하는가?
- 불필요한 Mutable Collection을 사용하지 않는가?
- Java 스타일 Getter와 Setter를 작성하지 않는가?
- `let`, `run`, `apply`, `also`를 과도하게 중첩하지 않는가?

## 13. Kotlin과 JPA

- Entity에 `data class`를 사용하지 않는가?
- JPA 프록시와 지연 로딩을 고려했는가?
- `equals`와 `hashCode` 구현이 안전한가?
- 연관관계 무한 순환이나 Entity 직접 직렬화 가능성이 없는가?
- 양방향 연관관계의 일관성을 유지하는가?

## 14. Migration

- 이미 적용된 Migration 파일을 수정하지 않는가?
- Migration 버전이 중복되지 않는가?
- NOT NULL 컬럼 추가 시 기존 데이터 처리 방안이 있는가?
- 컬럼 삭제와 이름 변경이 하위 호환성을 깨뜨리지 않는가?
- Entity 변경과 Migration이 함께 반영됐는가?

## 15. 중요 위험 신호

다음 항목은 실제 문제가 확인되면 우선적으로 보고한다.

- 인증 또는 인가 검증 누락
- 민감 정보 및 토큰 로그 출력
- 트랜잭션 누락으로 인한 데이터 정합성 문제
- 동시 참여로 인한 금액 또는 참여 인원 유실
- Unique Constraint 부재로 인한 중복 데이터 생성
- 외부 API 응답 검증 누락
- 심각한 N+1 쿼리
- 이미 적용된 Migration 파일 수정
- `!!` 사용으로 인한 실제 NPE 가능성

## 리뷰 심각도

| 심각도 | 의미 |
|---|---|
| P0 Critical | 데이터 손실 또는 심각한 보안 취약점 |
| P1 High | 명확한 버그 또는 데이터 정합성 문제 |
| P2 Medium | 성능, 설계 또는 유지보수성 문제 |
| P3 Low | 가독성 또는 경미한 개선 사항 |

## 리뷰 출력 형식

각 문제를 다음 형식으로 작성한다.

```markdown
### [P1] 문제 제목

**위치**
- 파일명과 라인 번호

**문제점**
- 확인된 문제 설명

**영향**
- 문제가 발생하는 조건과 영향

**개선 방법**
- 구체적인 수정 방향
```

문제가 없으면 억지로 지적하지 않고 검토 범위와 남은 위험을 간단히 설명한다. 사용자 요청 없이 코드 수정, Commit, Push 또는 PR 생성을 수행하지 않는다.
