# GitHub PR 생성 커맨드

## 사용법

```text
/pr <이슈번호>
```

## 동작 순서

1. 현재 브랜치와 Git 상태를 확인한다.
2. 브랜치 타입에 따라 PR 대상 브랜치를 결정한다.
3. `git log`와 `git diff <base-branch>...HEAD`로 전체 변경 사항을 파악한다.
4. 브랜치명 또는 `$ARGUMENTS`에서 Issue 번호를 확인한다.
5. 변경 사항을 분석해 아래 PR 템플릿을 작성한다.
6. 빌드 및 테스트를 실행하고 결과를 확인한다.
7. 사용자에게 PR 초안을 보여주고 생성을 확인한다.
8. 필요한 커밋의 원격 Push 상태를 확인하고 PR을 생성한다.
9. 수정 요청이 있으면 반영한 뒤 다시 확인한다.
10. 생성 완료 후 PR URL을 출력한다.

## Base Branch 규칙

| 브랜치 타입 | Base Branch |
|---|---|
| `feat` | `develop` |
| `fix` | `develop` |
| `refactor` | `develop` |
| `docs` | `develop` |
| `test` | `develop` |
| `chore` | `develop` |
| `hotfix` | `main` |
| 정식 배포 | `main` |

- `hotfix` 병합 후 동일한 변경 사항을 `develop`에도 반영해야 함을 안내한다.
- 정식 배포 PR은 `develop`에서 `main`으로 생성한다.
- 그 외의 경우 대상 브랜치를 임의로 변경하지 않는다.

## PR 템플릿

```markdown
## 🧾 요약
-

## 🔗 관련 이슈
- close #

## 📌 작업한 내용
-
-

## 🔍 참고 사항
-

## ✅ 체크리스트
- [ ] 로컬에서 빌드 및 테스트 완료
- [ ] 코드 리뷰 반영 완료
- [ ] 문서화 필요 여부 확인
```

## 각 항목 작성 규칙

### PR 제목 형식

| 제목 형식 | 용도 |
|---|---|
| `[Feat] 펀딩 개설 기능 추가` | 새로운 기능 |
| `[Fix] 펀딩 참여 금액 검증 오류 수정` | 버그 수정 |
| `[Hotfix] 결제 승인 오류 긴급 수정` | 운영 긴급 수정 |
| `[Refactor] 펀딩 서비스 구조 개선` | 리팩터링 |
| `[Chore] Claude Code 설정 추가` | 설정 및 기타 |
| `[Docs] API 문서 수정` | 문서 |
| `[Test] 펀딩 참여 테스트 추가` | 테스트 코드 |

### 🧾 요약

- PR이 무엇을 왜 하는지 한 줄로 작성한다.
- 예: `펀딩 개설 API 구현 — 사용자가 선물 펀딩을 생성할 수 있도록`

### 🔗 관련 이슈

- 브랜치명 또는 인자에서 확인한 Issue 번호를 연결한다.
- 예: `close #156`
- Issue 번호를 알 수 없으면 사용자에게 확인한다.
- 여러 PR이 하나의 Issue를 공유하면 자동 종료 여부를 확인한다.

### 📌 작업한 내용

- 실제 변경 내용을 기능 단위로 나열한다.
- 커밋 메시지를 그대로 복사하지 않는다.

예시:

- `펀딩 개설 요청 및 응답 DTO 추가`
- `펀딩 메시지 저장 로직 구현`
- `펀딩 참여 금액 검증 추가`

### ✅ 체크리스트

- 실제 실행 결과를 기준으로 작성한다.
- 빌드나 테스트에 성공한 경우에만 완료로 표시한다.
- 실행하지 않은 항목은 체크하지 않는다.
- 실패한 항목은 체크하지 않고 원인을 별도로 안내한다.

## PR 생성 명령

사용자 확인 후 본문을 임시 파일에 작성하고 `--body-file`로 전달한다.

```bash
BODY_FILE=$(mktemp)

cat > "$BODY_FILE" << 'EOF'
<채워진 템플릿 내용>
EOF

gh pr create \
  --title "[<타입>] <한글 제목>" \
  --body-file "$BODY_FILE" \
  --base "<base-branch>" \
  --assignee "@me"

rm -f "$BODY_FILE"
```

## Merge Strategy

- Merge Commit 방식을 사용한다.
- Squash Merge와 Rebase Merge는 사용하지 않는다.
- 사람의 Approve를 필수로 요구하지 않는다.
- CodeRabbit 자동 리뷰를 활용한다.
- CI 빌드와 테스트가 통과한 후 병합한다.

## 주의사항

- `main`, `develop`에서 직접 기능 개발 PR을 생성하지 않는다.
- 사용자 확인 없이 PR을 생성하거나 Push하지 않는다.
- PR 생성 후 자동으로 Merge하지 않는다.
- CodeRabbit의 모든 제안을 무조건 반영하지 않는다.
- 버그, 보안, 데이터 정합성 관련 리뷰를 우선 검토한다.
